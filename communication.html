Real-Time Control Communication

How the desktop control scripts talk to the MyCobot Pro 630 robot arm — mycobot_mpc

One-line summary: A desktop client streams target joint angles as JSON over TCP to a Python HAL component running inside LinuxCNC on a Raspberry Pi. That component computes per-loop position & velocity commands, writes them onto LinuxCNC HAL pins, which a real-time servo thread relays over a CAN bus to the joint motor drivers. Encoder feedback flows back the same path.

1System Overview

This is a two-machine distributed control system. High-level planning happens on a desktop; hard real-time motor control happens on a Raspberry Pi running an RT-patched Linux kernel with LinuxCNC. The two halves are connected by a plain TCP/JSON link; everything below the HAL boundary on the Pi is real-time.

2End-to-End Data Path

A single command travels through five layers. Each layer runs at its own rate; the boundaries are where the transport changes (TCP → HAL pins → CAN).

① Desktop clientTCPcontrol_robot.py · event-driven
  • Optionally solves IK (ik_pyroki.py) to turn a Cartesian goal into 6 joint angles.
  • Opens a TCP socket to the robot at $ROBOT_IP:9998 (TCP_NODELAY set), then sendall() of one newline-terminated JSON line per move (control_robot.py:251–259).

② ctrl component — command server & control loopHAL userspacerobot_hal.py · ~50 Hz (20 ms)
  • A server thread receives the JSON, validates target_deg, and pushes it onto an internal queue, replying {"state":"ack"} (robot_hal.py:595–598).
  • The main loop dequeues the target and runs run_control_loop() until converged or the duration expires (robot_hal.py:425–502). Each iteration:
poll  →  s.poll(); read joint_actual_position + pro600.joint*_velfb/torqfb
solve →  pid_solve | invdyn_solve | pd_velff_solve   (numpy, per-joint)
write →  h["joint{i}_pos_cmd"], h["joint{i}_vel_cmd"]   ← HAL OUT pins
sleep →  pad to the 20 ms period; check convergence (err < pos_tol)

Three selectable control laws: PID (pos-error + integral), InvDyn (PD position steps + optional gravity comp from invdyn_params.npz), PD + velocity feed-forward. Output is clamped to ±8°/step.

3The Key Mechanism: HAL Pins & the ctrl.enable Multiplexer

The bridge between "soft" Python and "hard" real-time control is the HAL (Hardware Abstraction Layer). robot_hal.py registers a userspace component named ctrl and exports pins (robot_hal.py:674–679): 

h = hal.component("ctrl")
for i in range(6):
    h.newpin(f"joint{i}_pos_cmd", hal.HAL_FLOAT, hal.HAL_OUT)
    h.newpin(f"joint{i}_vel_cmd", hal.HAL_FLOAT, hal.HAL_OUT)
h.newpin("enable", hal.HAL_BIT, hal.HAL_OUT)
h.ready()

Writing h["joint0_pos_cmd"] = … in Python instantly updates a value in LinuxCNC's shared-memory space. The RT servo thread reads it the same cycle. The elerob.hal wiring routes it through a per-joint 2-input mux selected by ctrl.enable: 

# elerob.hal — joint 0 position command path
net sig0-mot-pos-cmd joint.0.motor-pos-cmd => mux-gen.00.in-float-00   # source 0: LinuxCNC planner
net ctrl-j0-cmd      ctrl.joint0_pos_cmd   => mux-gen.00.in-float-01   # source 1: Python ctrl
net ctrl-enable      ctrl.enable           => mux-gen.00.sel-bit-00    # selector
net pid0-cmd         mux-gen.00.out-float  => pid.0.command pro600.joint0_motor_poscmd
This design lets the same machine be driven either by LinuxCNC's G-code trajectory planner or by the custom Python control law, switched live with a single bit. The Python side never touches CAN directly — it only sets HAL pins, and LinuxCNC's RT layer guarantees the timing down to the motors.

The Python control law runs in userspace at ~50 Hz, not in the hard-RT servo thread. That is acceptable because the downstream PID + CAN servo loop (10 ms) and the driver firmware (kHz) provide the tight, low-latency control. Per-loop timing (poll_ms, solve_ms, hal_write_ms, sleep_ms) is logged to CSV for every run.

5Startup & Enable Handshake

  1. linuxcnc elerob.ini loads elerob.hal, which loadusr-launches robot_hal.py --controller invdyn --params logs/invdyn_params.npz as the ctrl component (elerob.hal:17).
  2. robot_hal.py exports its HAL pins, starts the TCP command (9998) & stream (9999) servers, then runs enable_machine(): ESTOP-reset → pro600.poweron → wait for svr_poweroned / svr_enabled → home joints.
  3. It reads stable encoder feedback, pre-loads joint{i}_pos_cmd with the current position (so there is no jump), then asserts ctrl.enable = TRUE — which simultaneously flips the muxes and enables the PIDs (robot_hal.py:370–377, elerob.hal:596).
  4. The desktop connects to :9998 and begins sending target poses.
